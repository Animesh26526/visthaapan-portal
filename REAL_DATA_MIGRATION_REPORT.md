### 1. Overview & Objectives

The primary objective of this migration pass is to eliminate synthetic frontend mock dependencies, deprecate silent fallback routines that disguised backend disconnection, and enforce an unambiguous, audit-compliant **Provenance Badging System** across the entire VISTHAAPAN architecture.

Disaster management decision support requires absolute data integrity: an Incident Commander must never be misled into confusing a simulated planning benchmark with observed ground reality, nor should a system failure silently default to hardcoded fictional victims.

---

### 2. Frontend Mock Elimination & API Wiring

#### 2.1 Configuration Default Inversion
- **File:** `frontend/src/services/config.ts`
- **Previous State:** `export const USE_MOCK_API = import.meta.env.VITE_USE_MOCK_API !== 'false';` (defaulted to `true` in standard environments).
- **Current State:** `export const USE_MOCK_API = import.meta.env.VITE_USE_MOCK_API === 'true';` (strictly defaults to `false`, prioritizing live backend PostgreSQL APIs).

#### 2.2 Elimination of Silent Fallback Routines
In legacy services, catch blocks silently returned static in-memory mock datasets (e.g., `catch { return mockHabitations; }`). This masked network, database, or validation failures. All services have been refactored:
- **`HabitationsService` (`frontend/src/services/habitations.service.ts`):** Queries `/api/v1/habitations`. Database errors throw cleanly rather than returning mock villages.
- **`SitesService` (`frontend/src/services/sites.service.ts`):** Queries `/api/v1/sites`. Evaluates real capacity assessments from Phase 7.
- **`DecisionsService` (`frontend/src/services/decisions.service.ts`):** Records orders directly to PostgreSQL `officer_decisions` and `decision_history`.
- **`ScenariosService` (`frontend/src/services/scenarios.service.ts`):** Invokes live Google OR-Tools solver on backend and returns dynamic before/after deltas.
- **`EvidenceService` (`frontend/src/services/evidence.service.ts`):** Newly created service connecting directly to Chamoli DDMP 2026–27 documentary knowledge and the system provenance registry.

### 3. Explicit Data Provenance & Badging Standard

Every dataset and API response in VISTHAAPAN is classified under five mutually exclusive provenance categories:

| Provenance Badge | Description | Applied Datasets | Legal / Operational Impact |
|---|---|---|---|
| **`REAL`** | Observed, published, or legally enacted administrative records from authoritative government agencies. | • Canonical Districts (785, Census/LGD)<br>• Disaster Events (47,621, NDEM MHA)<br>• DDMP 2026–27 Evidence (30 records, DDMA Chamoli)<br>• Officer Adjudications (PostgreSQL audit ledger) | Legally binding records; primary operational evidence. |
| **`REAL (HISTORICAL 2011)`** | Verified historical baseline data. | • Census 2011 Demographics (640 districts) | **Baseline comparison only.** Strictly prohibited from being presented as current 2026 population counts. |
| **`QUARANTINED`** | Data where geographic attributes are verified, but operational capacity attributes lack verified live telemetry. | • National Healthcare Facility Geo-Registry (30,273 facilities) | **`HEALTHCARE_BED_DATA_QUARANTINED`**: Hospital coordinates are verified; bed counts are quarantined to prevent dangerous planning assumptions during mass-casualty events. |
| **`UNAVAILABLE`** | Geospatial or physical layers absent for the designated operational sector. | • Cartosat-1 Digital Elevation Model (DEM) | **`TERRAIN_ELEVATION_UNAVAILABLE_OUTSIDE_GUJARAT`**: DEM slope is available only for Western Gujarat tiles. In Chamoli, slope uses neutral heuristics with explicit audit disclosure. |
| **`DERIVED`** | Algorithmic outputs generated by machine learning or spatial geometry engines. | • Phase 5 Relative Priority Weights (XGBoost)<br>• Phase 6 GIS Multi-Hazard Buffer Unions (PostGIS) | Decision-support risk indicators; not statutory hazard proclamations. |
| **`SIMULATED_BENCHMARK`** | Modeled planning parameters based on international humanitarian minimums (Sphere standards). | • Phase 7 Shelter Carrying Capacities (Water, Sanitation, Area)<br>• Phase 8 OR Transit Allocations (OR-Tools MILP) | Staging benchmarks for scenario evaluation; requires Incident Commander review and verification before field execution. |
